## **КРАЕУГОЛЬНЫЙ КАМЕНЬ: АРХИТЕКТУРНЫЕ РЕШЕНИЯ ДЛЯ Z80 LISP СИСТЕМЫ**

### **1. ФИЛОСОФСКАЯ ОСНОВА: УПРАВЛЕНИЕ ПРОЦЕССАМИ**

**Исходный вопрос:** Как создать среду, где геймдизайнер мыслит в терминах взаимодействующих процессов?

**Наше решение:** Кооперативная многозадачность на уровне виртуальной машины с примитивами для работы с процессами.

**Обоснование:**
```lisp
;; Вместо монолитного кода - независимые процессы
(defprocess (enemy-ai enemy)
  (loop
    (patrol-area enemy)
    (sleep 2.0)
    (when (sees-player? enemy)
      (spawn attack-process enemy))
    (yield)))

(defprocess (player-input)
  (loop
    (handle-controls)
    (yield)))
```
*Причина:* Виртуальная машина обеспечивает изоляцию и контролируемость процессов, предотвращая краши всей системы.

### **2. ВЫБОР АРХИТЕКТУРЫ: OPENGOAL VS UNCHARTED**

**Исходный вопрос:** Какой путь выбрать - самодостаточный Lisp или гибрид с C++?

**Наше решение:** Uncharted-путь (гибридный) с виртуальной машиной.

**Обоснование:**
- **Контролируемость:** Байт-код ВМ не может "уронить" всю систему
- **Отладка:** Предсказуемая отладка на уровне ВМ вместо хаотичной отладки нативного кода
- **Производительность:** C++ для низкоуровневых задач, Lisp для логики
- **Практичность:** Разделение ответственности в маленькой команде

**Архитектура:**
```
[PC: Инструменты] → [Z80 Картридж]
    ↓                     ↓
Lisp компилятор    →   ВМ + Байт-код
    ↓                     ↓
C++ компилятор    →   Нативные модули
```

### **3. ДИЛЕММА КОМПИЛЯЦИИ: КРОСС- VS НАТИВНАЯ**

**Исходный вопрос:** Где выполнять тяжелые вычисления - на PC или на Z80?

**Наше решение:** Кросс-компиляция на PC с легковесным рантаймом на Z80.

**Обоснование:**
- Z80 не справится с сложными инструментами (парсеры, генераторы кода)
- Быстрые циклы разработки на PC
- На Z80 - только исполнение оптимизированного байт-кода

---

### **4. СИСТЕМА ТИПОВ: МОЩНОСТЬ VS ПРАКТИЧНОСТЬ**

**Исходный вопрос:** Насколько богатой должна быть система типов?

**Наше решение:** Практичная система типов для игровых нужд.

**Минимальный набор типов:**
```lisp
;; Базовые типы
:int8, :int16, :uint8, :uint16
:boolean, :string, :symbol

;; Структуры
(defstruct vec2 (x :int16) (y :int16))
(defstruct entity 
  (position vec2)
  (sprite-id :uint8)
  (flags :bitfield 8))

;; Коллекции
(defarray level-data :uint8 1024)  ;; inline массив
(deflist active-entities entity)   ;; динамический список
```

*Причина:* Сложные системы типов требуют сложной runtime-поддержки, что непрактично для Z80.

### **5. УПРАВЛЕНИЕ ПАМЯТЬЮ: ХИП VS СТРАНИЧНАЯ ОРГАНИЗАЦИЯ**

**Исходный вопрос:** Как организовать память на Z80 с ограниченными ресурсами?

**Наше решение:** Страничная организация вместо единого хипа.

**Обоснование:**
```c
// Изоляция модулей через страницы
struct module_page {
    uint8_t page_id;
    uint8_t* code_start;
    uint8_t* data_start;
    struct type_table* types;
};
```

*Причина:* Избегаем сложного GC и фрагментации памяти. Модули могут загружаться/выгружаться независимо.

### **6. ИНСТРУМЕНТЫ РАЗРАБОТКИ: ХОСТ VS ЦЕЛЕВАЯ ПЛАТФОРМА**

**Исходный вопрос:** Где должны находиться средства разработки?

**Наше решение:** Разделение на Host-инструменты и Client-shell.

**Архитектура инструментов:**
```
[PC: Полная среда разработки]
    - Компилятор Lisp → байт-код
    - Отладчик
    - Профайлер
    ↓
[Z80: Минимальный Lisp Shell]  
    - Загрузчик модулей
    - Базовый REPL
    - Системные команды
```

**Пример shell на Z80:**
```lisp
>> (ls "A:")
(GAME1.ZBC GAME2.ZBC SAVE.DAT)

>> (load-debug "GAME1.ZBC")
Debug symbols loaded

>> (trace 'update-player)
>> (run)
```

*Причина:* Сохраняем интерактивность разработки без неподъемных для Z80 инструментов.

### **7. ОТЛАДОЧНАЯ ФИЛОСОФИЯ**

**Исходный вопрос:** Как сделать отладку максимально эффективной?

**Наше решение:** Многоуровневая отладка с фокусом на уровне ВМ.

**Возможности отладки:**
```lisp
;; Контролируемое выполнение
>> (vm-step 5)           ;; 5 шагов байт-кода
>> (break-at 'collision) ;; Точки останова
>> (inspect *player*)    ;; Инспекция объектов

;; Hot-reload
>> (reload "fixed-ai.zbc") ;; Перезагрузка без перезапуска
>> (continue)              ;; Продолжить выполнение
```

*Причина:* Отладка байт-кода ВМ предсказуема и безопасна compared to отладка нативного Z80 кода.

## **ИТОГОВАЯ АРХИТЕКТУРА:**

```lisp
;; Система строится вокруг процессов
(defgame my-game
  (processes
   (player-input-process)
   (enemy-ai-process)
   (physics-process)
   (render-process)))

;; С компиляцией на PC
(compile-game "my-game"
  :target :z80
  :output "game.zbc"
  :debug "game.zd")

;; И выполнением на Z80
>> (load-and-run "game.zbc" "game.zd")
```

**Ключевое преимущество:** Мы получаем выразительность Lisp с безопасностью и контролируемостью виртуальной машины, что критически важно для ограниченной платформы Z80.
